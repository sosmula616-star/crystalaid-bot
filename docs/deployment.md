# Развёртывание

Существуют API, worker, бот (`apps/bot`) и Activity (статический клиент, см. последний раздел).

## Требования

- Node.js и pnpm, `pnpm install --frozen-lockfile`.
- PostgreSQL (проверено на 18).
- Redis 5 или новее. Используются только команды Redis 5 (потоки, `XCLAIM`); `docker-compose.yml` поднимает Redis 7.

## Настройка

1. Переменные окружения (образец: `.env.example`). API и worker при старте читают `.env` из корня репозитория, если файл есть (`apps/api/src/main.ts`, `process.loadEnvFile`). Переменные, заданные в настоящем окружении, сильнее файла, поэтому менеджер процессов может переопределить любую. `pnpm db:migrate` файл `.env` тоже читает. Переменные:

   | Переменная | Смысл |
   |---|---|
   | `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, `DISCORD_BOT_TOKEN` | приложение Discord |
   | `DISCORD_API_URL` | по умолчанию `https://discord.com/api/v10` |
   | `DATABASE_URL`, `REDIS_URL` | подключения; в `REDIS_URL` должен быть пароль |
   | `POSTGRES_PASSWORD`, `REDIS_PASSWORD` | пароли для `docker-compose.yml` (только для него; сервисы читают их из URL) |
   | `JWT_SECRET`, `SERVICE_TOKEN` | секреты, не короче 32 символов; `SERVICE_TOKEN` один и тот же у API и бота |
   | `DISCORD_BOT_TOKEN`, `DISCORD_CLIENT_ID` | бот читает оба; `DISCORD_CLIENT_ID` нужен для `register` |
   | `API_URL` | адрес API для бота; по умолчанию `http://127.0.0.1:PORT` |
   | `TRUSTED_PROXIES` | адреса или CIDR обратных прокси через запятую; пусто: не доверять никому |
   | `PORT` | порт API, по умолчанию 3001 |
   | `CONFIG_PATH` | путь к файлу конфигурации сервера (необязательно) |

2. Конфигурация сервера: скопировать `crystalaid.config.example.json` в `crystalaid.config.json` в корне репозитория (файл в git не попадает) или указать путь в `CONFIG_PATH`. В нём гильдия, часовой пояс, роли поддержки, куратора и администратора и каналы. Один идентификатор роли не может стоять в двух списках.

3. Миграции: `pnpm db:migrate` (берёт `DATABASE_URL`). `tsx` входит в зависимости пакета `packages/database`, поэтому команда работает и после `pnpm install --prod`.

## Запуск

Сервисы работают прямо из исходников через tsx, без сборки. `pnpm build` собирает Activity и требует `VITE_DISCORD_CLIENT_ID`.

```
pnpm --dir apps/api run api
pnpm --dir apps/api run worker
```

```
pnpm --dir apps/bot run register   # один раз и после смены команд: /help, /menu, /dev
pnpm --dir apps/bot run start
```

Бот читает корневой `.env` так же, как API (полная последовательность первого запуска: [Запуск бота с нуля](#запуск-бота-с-нуля)), и использует `REDIS_URL` для потока `events:bot` и коротких записей (`bot:ticket:*`, 24 часа). Ему нужны интенты Guilds, Server Members и Direct Messages (Server Members требует заявки в Developer Portal при 10 000 и более участников) и право писать в `channels.log`. Все три процесса завершаются по SIGTERM и SIGINT.

Worker можно запускать в нескольких экземплярах: общая группа Redis делит события между ними. API слушает `0.0.0.0:PORT`. `GET /health` подходит для проверки живости.

## Запуск бота с нуля

Порядок важен: бот без API ничего не сделает, а ПТ назначить можно только после того, как бот передал состав ветки. Сначала пройдите всё на закрытом тестовом сервере (последний раздел), потом повторите на настоящем.

1. **Developer Portal** (discord.com/developers/applications). Создайте приложение. Вкладка Bot: сбросьте токен и сохраните его (это `DISCORD_BOT_TOKEN`), включите **Server Members Intent** в Privileged Gateway Intents. Message Content и Presence не нужны. Для сервера на 10 000 и более участников этот интент выдаётся только после заявки в Developer Portal: подайте её заранее, без интента бот не видит смену ролей и снимок состава приходит пустым. `DISCORD_CLIENT_ID` это Application ID на вкладке General Information.
2. **Приглашение на оба сервера**: основной (`guildId`) и сервер с логом, если он другой. OAuth2, URL Generator: scopes `bot` и `applications.commands`. Права: на основном сервере достаточно просмотра каналов; в канале `channels.log` боту нужны View Channel, Send Messages, Attach Files, Embed Links (файлы стенограмм, копии вложений и сводки). Права на личные сообщения серверу не нужны, но каждый получатель должен разрешить личные сообщения от участников сервера. При старте бот проверяет канал лога и останавливается с понятной ошибкой, если не видит его или не может писать.
3. **Полный `.env`** в корне репозитория (образец `.env.example`). Бот читает: `DISCORD_BOT_TOKEN`, `DISCORD_CLIENT_ID`, `SERVICE_TOKEN` (не короче 32 символов, тот же, что у API), `REDIS_URL` (с паролем), `API_URL` (если API не на `127.0.0.1:PORT`). API и worker читают ещё `DISCORD_CLIENT_SECRET`, `DATABASE_URL`, `JWT_SECRET`, `TRUSTED_PROXIES`, `PORT`, `DISCORD_API_URL`. Все значения заполнены, образцов вроде `replace-with-...` не осталось.
4. **`crystalaid.config.json`**: копия `crystalaid.config.example.json` со своими значениями. `guildId` основной сервер; `timezone` например `Europe/Moscow` (по нему считаются часы ПТ); `roles.support` и `roles.curator` идентификаторы ролей, куратору нужны обе роли; `users.admins` и `users.developers` идентификаторы аккаунтов (разработчики получают `/dev` и права администратора); необязательный `roles.admin` даёт уровень админа ролью, обычно он не нужен; `channels.help` канал, где работает `/help`; `channels.log` канал лога, он может быть на другом сервере. Режим разработчика Discord показывает идентификаторы через «Копировать ID».
5. **Миграции**: `pnpm db:migrate`.
6. **Запуск по порядку**, каждый процесс в своём окне или под супервизором:

   ```
   pnpm --dir apps/api run api
   pnpm --dir apps/api run worker
   pnpm --dir apps/bot run register   # один раз и после смены списка команд; завершается сам
   pnpm --dir apps/bot run start
   ```

   `/menu`, `/dev` и `/help` это команды сервера, в личных сообщениях с ботом их нет.
7. **Дождитесь строки `roster snapshot published`** в выводе бота (`[bot] roster snapshot published: N members (startup)`). Бот отправляет снимок состава через Redis, worker применяет его; до этого в базе нет ни одного сотрудника и `/menu` отвечает «Нет доступа». Если строки нет, смотрите вывод: бот повторяет снимок с паузами (учитывает `retry_after` Discord) и пишет каждую неудачу; частая причина это выключенный Server Members Intent. Снимок повторяется после потери сессии и раз в сутки.
8. **Назначьте первое ПТ**: администратор (id из `users.admins`) вызывает `/menu`, раздел «Расписание ПТ», выбирает дату, сотрудника и час. Пока на часе никого нет, тикеты ждут и предлагаются в начале ближайшего ПТ. Назначить можно только того, кто уже попал в базу (шаг 7).
9. **Супервизор**. API, worker и бот должны подниматься сами. Пример для systemd, один юнит на процесс (для API и worker меняется только `ExecStart`):

   ```
   [Unit]
   Description=CrystalAid bot
   After=network-online.target

   [Service]
   WorkingDirectory=/srv/crystalaid
   ExecStart=/usr/bin/pnpm --dir apps/bot run start
   Restart=always
   RestartSec=5
   User=crystalaid

   [Install]
   WantedBy=multi-user.target
   ```

   Подойдёт и pm2 с `--restart-delay`. Остановка идёт сигналом SIGTERM (бот сам закрывает соединения). Бот переподключается к Discord сам; перезапуск процесса безопасен: напоминания ПТ не теряются (они отмечаются отправленными только после доставки), предложения тикетов повторяются каждые 5 минут с теми же заданиями.

### Закрытый тестовый сервер перед настоящим

1. Создайте приватный сервер (и, если нужно, второй для лога), отдельное приложение Discord или то же, но приглашённое на тестовые серверы. Отдельные база и Redis (`DATABASE_URL`, `REDIS_URL`) или хотя бы отдельная база.
2. Отдельный файл конфигурации: `CONFIG_PATH=crystalaid.test.config.json` с тестовыми id (роли, каналы `help` и `log`, ваш id в `users.admins`).
3. Пройдите шаги 1 до 9 выше. Затем проверьте руками, на двух-трёх тестовых аккаунтах: `/help` только в `channels.help`; тикет доходит до саппорта на ПТ с четырьмя картинками; неверный ответ закрывает возможность взять именно этот тикет; второй тикет у занятого саппорта даёт «Сначала закройте текущий тикет»; кнопка «Отменить» работает до принятия; закрытие даёт оценку и файл стенограммы в канале лога; вложение появляется в канале лога; `/menu` (открытые тикеты: закрыть, вернуть в очередь; ошибки доставки); закрытые личные сообщения попадают в «Ошибки доставки»; снятие роли у принявшего саппорта возвращает его тикет в очередь; напоминание за 5 минут до ПТ.
4. Автозакрытие через 24 часа без движения проверьте, сдвинув в тестовой базе `tickets.last_activity_at` на сутки назад.
5. Только после этого повторите шаги на настоящем сервере с настоящими `.env` и `crystalaid.config.json`.
## Redis

Redis это граница доверия. Любой, кто может писать в поток `events:bot`, может выдать себе роль администратора: событие `member.updated` с ролью администратора из `crystalaid.config.json` создаёт запись ADMIN, а у администратора есть все права, включая настройки и права ролей. Поэтому в рабочей среде Redis должен быть закрыт от сети и защищён паролем (`requirepass` и пароль в `REDIS_URL`). Не публикуйте порт Redis наружу. `docker-compose.yml` привязывает порты PostgreSQL и Redis к `127.0.0.1`, пароли берёт из `POSTGRES_PASSWORD` и `REDIS_PASSWORD`. Писать в `events:bot` должен только бот. См. [security.md](security.md).

## Обратный прокси

- В `TRUSTED_PROXIES` нужно перечислить адреса прокси. Если оставить пусто, API видит адрес прокси вместо адреса клиента, и все клиенты делят один счётчик лимита входа (10 в минуту).
- Порт API не должен быть доступен напрямую, когда есть прокси: в обход прокси пропадают его TLS и фильтрация. Откройте порт только для прокси (файрвол или привязка к внутренней сети). Адрес вне `TRUSTED_PROXIES` не может подменить адрес клиента через `X-Forwarded-For`.
- Прокси завершает TLS; API его не обслуживает.
- Трафик Activity к API приходит через прокси Discord. Его адреса, возможно, нельзя перечислить в `TRUSTED_PROXIES`. Тогда API увидит один и тот же адрес у всех и все входы поделят один счётчик лимита (10 в минуту). Это проверяется при первом запуске (см. список ниже); до тех пор решение не принято.

## Известные ограничения

Перечислены в [security.md](security.md). Из эксплуатационных: события, не обработанные за 5 попыток, лежат в `events:dead` и требуют ручного разбора.

## Activity (статика)

Activity это статические файлы, сервера у неё нет.

1. Задать `VITE_DISCORD_CLIENT_ID` (идентификатор приложения Discord, тот же, что `DISCORD_CLIENT_ID`). Значение вшивается в сборку: его читают при сборке из корневого `.env` или из окружения, после сборки сменить нельзя. Если значение пусто, `vite build` завершается ошибкой с пояснением (режим `mock` не собирается в продакшен). Из `.env` в клиент попадают только переменные с префиксом `VITE_`; секреты (`DISCORD_CLIENT_SECRET`, `JWT_SECRET`) туда не попадают.
2. Собрать: `pnpm --dir apps/activity run build` (проверка типов и `vite build`). Результат в `apps/activity/dist`: `index.html` и `assets/`. Шрифт и значки лежат внутри, внешних запросов нет, кроме доменов Discord из SDK (в файлах есть ещё строки библиотек: `www.w3.org`, `json-schema.org`, `react.dev`, `github.com`, `localhost`, они не запрашиваются).
3. Разместить `dist` на любом статическом хостинге с HTTPS. Для кэша хватит значения по умолчанию: имена файлов в `assets/` содержат хэш, `index.html` кэшировать не нужно.
4. В портале разработчиков Discord, раздел Activities, URL Mappings:

   | Префикс | Цель |
   |---|---|
   | `/` | адрес статического хостинга без `https://` |
   | `/api` | адрес API (прокси перед `apps/api`) |

   Activity обращается к `/api/...`, Discord передаёт запрос по цели без префикса `/api`, поэтому у API нет префикса в маршрутах (`/me`, `/auth/activity`). Тот же адрес работает в разработке: `vite` проксирует `/api` на `127.0.0.1:3001`.
5. Подставной режим и витрина `/kit` в сборку не входят; это проверяет `pnpm --dir apps/activity run test:e2e` (`bundle.spec.ts`).

### Первый запуск в Discord

Проверить по порядку, на настоящем сервере. Локально это не воспроизводится.

1. Адрес API: установленный SDK 2.5.0 не обрабатывает `.proxy` сам. В первом настоящем запуске проверить в сетевой вкладке, что запросы доходят до API через URL Mapping (`/api/...`, API получает `/auth/activity`). Если Discord требует префикс `/.proxy`, изменить `baseUrl` в клиенте API.
2. Настоящая CSP: Discord выдаёт Activity собственную политику, которой на локальном `vite` нет. Открыть Activity в Discord с консолью и убедиться, что нет ошибок CSP: шрифт, изображения и скрипты грузятся только со своего адреса.
3. Окно согласия: при первом входе Discord показывает диалог с запросом `identify` и `guilds`. Нужно прочитать его и принять; на это даётся 5 минут, потом вход заканчивается ошибкой подключения. Повторный вход проходит без диалога.
4. Режим «поверх чата» (PIP) при старте: запустить Activity уже свёрнутой и убедиться, что показывается компактный вид, а после разворота возвращается обычный.
5. `TRUSTED_PROXIES`: сделать несколько входов с разных учётных записей и проверить в журнале API, что адреса клиентов различаются. Если у всех один адрес, входы делят один счётчик лимита (10 в минуту), и адреса прокси Discord нужно добавить в `TRUSTED_PROXIES` или решить вопрос лимита иначе.

## Всё в одном контейнере (bothost)

Один контейнер запускает всё: бот, worker, API и Activity. `Dockerfile` в корне собирает клиент Activity, `scripts/start-all.mjs` (CMD) делает остальное, по порядку:

1. `CONFIG_JSON` пишется во временный файл (права 0600), `CONFIG_PATH` указывает на него; конфиг проверяется схемой, ошибка называет поле.
2. `SERVICE_TOKEN` и `JWT_SECRET` генерируются, если не заданы (после перезапуска значения новые). `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, `DISCORD_BOT_TOKEN`, `DATABASE_URL` обязательны.
3. Если `REDIS_URL` не задан, поднимается встроенный `redis-server` на 127.0.0.1 без сохранения на диск.
4. Один раз выполняются миграции, затем регистрируются команды Discord (сбой не фатален).
5. Запускаются API, worker и бот; упавший процесс перезапускается с паузой от 1 до 30 секунд. API слушает `0.0.0.0:PORT` (по умолчанию 3000), отдаёт Activity на `/`, API на `/` и `/api`, а `/internal` защищён сервисным токеном. Бот ходит в API на `http://127.0.0.1:PORT`.
6. По SIGTERM и SIGINT все процессы останавливаются меньше чем за 10 секунд.

В логе нет секретов: строки `схема://...` и значения секретных переменных заменяются.

### Настройка панели bothost

Репозиторий `crystalaid-bot`, ветка `main`, собственный Dockerfile включён, домен включён (HTTPS), порт `3000`. Переменные перечислены в [README](../README.md#развёртывание-на-bothost).
