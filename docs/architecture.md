# Архитектура

Реализовано ядро: HTTP API и worker, который применяет события Discord. Activity есть (`apps/activity`) и бот (`apps/bot`): тикеты в личных сообщениях, ПТ, `/menu` и `/dev`. Бот не ходит в базу, всю логику ведёт API через `/internal/*`; события состава бот кладёт в Redis, как описано ниже.

## Процессы

```
Бот (apps/bot)                     Activity (реализована)
   |  XADD events:bot                  |  POST /auth/activity, Bearer JWT
   v                                   v
 Redis 5+ ------------------------> API (Fastify) -----> PostgreSQL
   |  XREADGROUP (группа workers)        ^                    ^
   v                                     | Discord REST       |
 Worker (consumeBatch) -----------------+--------------------+
```

- **API** (`apps/api`, роль `api`): маршруты, проверка сессий, лимиты запросов. Ходит в PostgreSQL и Redis; в Discord обращается только при входе.
- **Worker** (роль `worker`): читает поток `events:bot` группой `workers`, применяет события к `staff_members`, пишет журналы.
- **PostgreSQL**: единственное хранилище состояния. **Redis**: поток событий, счётчики лимитов, служебные ключи снимков.

Оба процесса запускаются через tsx из одного кода (`apps/api/src/main.ts api|worker`).

## События

Бот кладёт в поток `events:bot` записи с одним полем `event`, в котором JSON: `XADD events:bot * event <json>`. Типы описаны в `packages/contracts/src/events.ts`:

| Тип | Действие worker |
|---|---|
| `member.updated` | пересчитать уровень по текущим ролям: создать запись, сменить уровень, вернуть или снять доступ |
| `member.removed` | снять доступ, история и баланс остаются |
| `member.snapshot` | часть полного списка участников (см. ниже) |

События другой гильдии пропускаются. Событие старше `staff_members.last_event_at` пропускается, поэтому повторная доставка не откатывает новое состояние.

Перед каждой пачкой worker выполняет `SELECT 1`. Если база недоступна, пачка прерывается ошибкой до `XCLAIM` и `XREADGROUP`, цикл пишет её в журнал и ждёт секунду: простой не расходует счётчик доставок и не отправляет события в `events:dead`.

Неактивная запись стаффа хранит уровень `NONE`; прежний уровень записан в `career_events` (тип `deactivated`, поле `level`). При возвращении уровень задаётся заново. Параллельные первые синхронизации одного человека безопасны: вставки `users` и `staff_members` идут с `ON CONFLICT DO NOTHING` и перечитывают строку.

Доставка: запись подтверждается (`XACK`) после успешной обработки. Ошибка обработчика оставляет запись в ожидании; через 60 секунд её забирает любой worker. Запись, доставленная больше 5 раз, неразбираемый JSON и событие, не прошедшее схему, переносятся в `events:dead` и подтверждаются. Автоматического повтора из `events:dead` нет.

## Протокол снимка

Полный список участников приходит частями.

- Каждая часть: `snapshotId`, `part` (с 1), `parts` (всего частей), `members`, `at`.
- `at` это момент начала перечисления гильдии, одинаковый или более ранний для всех частей.
- Части применяются в любом порядке. Каждый участник части синхронизируется как `member.updated` со временем `at`; затем идентификаторы части и её номер записываются в Redis одной транзакцией (`snapshot:<id>:members`, `:done`, `:at`).
- Когда записаны все `parts` частей, один worker (под блокировкой `:lock`) снимает доступ у активного стаффа, которого нет в объединённом наборе (причина `not_in_snapshot`). Отсечкой служит самый ранний `at` среди частей: любое более новое событие участника выигрывает.
- Метка `:applied` не даёт повторной доставке запустить снятие второй раз. Ключи живут час.
- Недостающая или не обработанная часть никого не деактивирует. Пустой снимок тоже.
- Первая пришедшая часть фиксирует `parts` в `snapshot:<id>:parts` (тот же срок жизни). Часть с другим `parts` отклоняется: в журнал пишется ошибка, участники части не синхронизируются и часть не записывается.
- Защита от обрезанного снимка: если снимок снял бы доступ больше чем у половины активного стаффа и не меньше чем у 3 человек, снятие не выполняется, в журнал пишется ошибка, метка `:applied` ставится (повторная доставка ничего не изменит).

## Вход

Activity присылает `code` и `instanceId`. API обменивает код на токен Discord, получает пользователя, проверяет экземпляр Activity (гильдия берётся только из него), читает роли участника, синхронизирует запись и выдаёт JWT на 15 минут. Подробнее: [security.md](security.md).
